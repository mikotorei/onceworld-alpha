## 担当の件数の上限を作り替える（挑戦は1つの Issue につき2回まで、一日の上限は設定値に）

ドキュメント「独立に向けた開発の管理」の体制設計タブ「上限の見直し」（2026-10-01 決定）による。計画の承認（A：完了できない判断と時間切れは1回目で止める、B：設定値 0 は止めるスイッチ、C：miko-hub の #11 の反映後の main から作る）を得て、miko-hub と onceworld-alpha の両方に同じ中身で入れた。

### なぜ
- 社長の使い方は、見つけた不具合や追加データをその都度出す形。1日3件の上限が、安全網ではなくブレーキになっていた。
- 担当の暴走は「同じ Issue を何度も拾い直して動き続ける」形しかないので、件数ではなく Issue ごとの挑戦の回数で止める。

### したこと
- 1つの Issue につき、自動の挑戦は2回まで（`rules.MAX_ATTEMPTS`）。
  - 挑戦の回数＝持ち主が最後に「着手可」を付けてから、担当が「作業中」を付けた回数（`rules.attempts_since`）。持ち主が付け直すと数え直し。
  - 1回目の失敗（変更が無い・日誌が無い・実行の失敗・提案を出せない など）は、担当が「着手可」に付け直してもう一度挑戦し、理由をコメントする。
  - 2回目の失敗は「案」に戻し、2回失敗したので止めた旨と理由をコメントする（`rules.gave_up_comment`）。
  - 担当が完了できないと判断した時と40分の時間切れは、やり直しても同じ結果になりやすいので、1回目でも「案」に戻す（`rules.failure_kind`・`rules.retry_after_failure`）。
  - 拾う時点で既に2回挑戦していれば、作業せずに「案」に戻す（念のための安全網）。
  - 持ち主の判定（`rules.ready_labeled_at`）では、担当が付け直した「着手可」を数えない。人が最後に付けたのが持ち主なら拾う。順番も持ち主が付けた時のまま。
- 一日の上限をリポジトリの設定値 `WORKER_DAILY_LIMIT`（Actions の Variables）にした（`rules.daily_limit`）。無い・空欄なら20件。0 は「着手しない」＝止めるスイッチ。数字以外やマイナスは20件で動かし、実行の記録に注意書きを出す。ワークフローの pick の手順に `vars.WORKER_DAILY_LIMIT` を渡す。
- 同時に1件・1件40分・miko-hub の月900分は変えていない。
- 文書：設定値の変え方と、0 が止めるスイッチになることを書いた。
- onceworld-alpha：CLAUDE.md の「担当の職務規定」の上限の行。詳しい経緯は miko-hub の journal/2026-10-01.md。

### 確かめたこと
- `python -m pytest worker/tests`：50件通過（labels.py が無いので1件は飛ばす）。actionlint：指摘なし。`worker/` は miko-hub と同じ中身。

### 残った課題
- 再挑戦は GitHub の上でしか確かめられない。次に担当が失敗した時の動きで確かめる。

## 担当が予定どおり止まった時、Actions の実行を「失敗」にしない

Issue #11 で担当が停止条件に当たって予定どおり止まった時、担当の実行が「失敗」で記録され、中心都市の見張りがそれを公開の失敗（「異常」）と数えた。原因の調べと修正は miko-hub の手元の Claude Code で行い、同じ変更を miko-hub にも入れた（詳しくは miko-hub の journal/2026-10-01.md）。

### したこと
- 予定どおりの停止（完了できないと判断・変更が無い・日誌が無い・ワークフローの変更を含む）は、finish が成功で終えて `stopped` の印を出し、fail の手順が動くようにした。実行そのものの失敗・時間切れは「失敗」のまま。
- もう一度挑戦するかの決まりは変えていない（変わるのは実行の結果の色だけ）。テストで確かめた。
- `worker/` を miko-hub と同じ中身にし、CLAUDE.md に1行足した。見張り側（担当のワークフローを公開処理として数えない）は miko-hub で直した。
